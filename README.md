# 제안서 평가 벤치마크

데이터 기반 업무 제안서를 **리더의 자리에서** 읽고, 고정된 6개 기준 100점으로 평가한다.
9주차 Day5 트랙 C 「나만의 벤치마크 앱」 실습으로, 강사가 배포한
`제안서_평가_벤치마크_제작_무료배포_가이드.pdf` 를 따라 만들었다.

이 앱의 요점은 **AI 에게 점수를 맡기지 않는 것**이다.
사람이 기준과 판정 규칙을 먼저 고정하고, AI 는 근거를 찾아 수준만 고른다.

| AI 가 하는 것 | 코드가 하는 것 |
| --- | --- |
| 문서에서 근거 구절을 찾는다 | 인용이 원문에 **정말 있는지** 대조한다 |
| 항목마다 0~4 수준을 고른다 | 수준 ÷ 4 × 배점으로 점수를 낸다 |
| 한국어로 판단과 고칠 것을 쓴다 | 총점과 판정을 계산한다 |

## 빠른 시작

```
npm install
cp .env.example .env.local     # PowerShell: Copy-Item .env.example .env.local
# .env.local 의 GEMINI_API_KEY 를 실제 키로 바꾼다
npm run dev:full
```

`http://127.0.0.1:3000` 을 연다.

> **`npm run dev` 가 아니라 `npm run dev:full` 이다.** `dev` 는 화면만 띄워서
> `/api/evaluate` 가 404 로 나온다. 가이드 12장 증상표의 첫 줄이 이것이라
> `server/dev.ts` 가 화면과 서버 함수를 **한 포트**에 같이 올린다.

배포 전에는 둘 다 통과해야 한다.

```
npm test          # 75건
npm run check     # 34건 — 시험이 못 보는 자리
npm run build
```

## 평가 기준

배점은 `src/lib/rubric.ts` 한 곳에서 온다. 아래 표는 그것을 옮겨 적은 것이고,
**`checks/run_all.ts` 가 이 표와 코드가 같은지 매번 다시 센다** (아래 「걸린 것」 참고).

| 항목 | 배점 | 핵심 질문 |
| --- | ---: | --- |
| 문제 정의 | 15 | 왜 지금 이 문제를 해결해야 하는가? |
| 데이터 근거 | 25 | 이 숫자를 의사결정에 믿고 써도 되는가? |
| 분석과 제안의 연결 | 20 | 분석 결과가 이 제안을 뒷받침하는가? |
| 실행 가능성과 효과 | 20 | 누가, 얼마로, 무엇을 달성하는가? |
| 리스크와 검증 | 10 | 틀렸을 때 어떻게 알아채고 멈출 것인가? |
| 의사결정 요청 | 10 | 무엇을 언제까지 승인해야 하는가? |

각 항목은 0~4 수준으로 보고 **수준 ÷ 4 × 배점**으로 환산한다.
한 수준을 잃으면 그 항목 배점의 **정확히 ¼** 을 잃는다 — 데이터 근거는 한 수준이 6.25점이다.

### 판정은 총점만으로 정하지 않는다

**데이터 근거가 수준 1 이하면 나머지가 만점이어도 「기각」이다.**
믿을 수 없는 숫자 위에 세운 제안은 잘 쓰였을수록 위험하다.
이 규칙이 없으면 다섯 항목을 잘 써서 81.25점으로 조건부 승인을 받을 수 있다.

| 조건 | 판정 |
| --- | --- |
| 데이터 근거 수준 ≤ 1 | 기각 (총점과 무관) |
| 85점 이상 + 의사결정 요청 수준 ≥ 3 | 승인 |
| 70점 이상 | 조건부 승인 |
| 50점 이상 | 보류 |
| 그 아래 | 기각 |

### 평가자 역할

사업부 리더 · 재무 책임자 · 운영 책임자 중에 고른다.
**관점은 바뀌고 배점은 안 바뀐다** — 역할마다 척도까지 달라지면 평가끼리 견줄 수 없다.

## 반드시 알아야 할 제한

1. **키는 Git 에도 브라우저에도 안 들어간다.** `.env.local` 은 `.gitignore` 에 있고,
   키 이름에 `VITE_` 를 붙이지 않는다 — 붙이면 번들에 들어간다.
   `npm run check` 가 빌드 결과물을 뒤져서 이것을 다시 본다.
2. **공개 배포는 내 할당량을 쓴다.** 로그인도 호출 제한도 없다.
   `BENCH_ACCESS_CODE` 를 넣으면 입장 코드를 요구한다. 켜 두는 쪽이 안전하다.
3. **무료 플랜은 무제한이 아니다.** Vercel Hobby 는 비상업적 개인 사용이고,
   Gemini Free Tier 의 모델·한도는 계정마다 다르다. 429 가 나면 그것이다.
4. **제안서 원문이 Google 로 간다.** 제목·도메인·본문·역할이 전달된다
   (작성자 이름은 안 보낸다). 개인정보·고객정보·미공개 재무자료를 그대로 넣지 않는다.
5. **이력은 이 브라우저 안에만 있다.** 다른 PC 와 안 맞춰지고, 브라우저 데이터를
   지우면 사라진다. 공용 PC 는 쓰고 나서 「이력 지우기」를 누른다.
6. **파일을 읽었다고 원자료가 검증된 것은 아니다.** 이 앱은 **문서가 설득력 있게
   쓰였는가**만 본다. 숫자가 사실인지는 확인하지 않는다. 성적에 그대로 쓰지 않는다.
7. **JavaScript 로 그리는 차트는 못 읽는다.** Plotly·Chart.js 의 수치는 `<script>`
   안에만 있다. 그래서 **일부러 버리고** 「차트를 못 읽었다」고 화면에 띄운다 —
   남겨 두면 본문에 없는 숫자가 본문에 있는 것처럼 읽힌다.

## 만들면서 걸린 것

검사와 시험이 잡아낸 것만 적는다. 안 걸린 것은 안 적는다.

| 무엇 | 어떻게 알았나 |
| --- | --- |
| **오류 문구에 키가 샐 수 있었다** | 400·500 응답은 Google 이 준 본문을 그대로 붙여서 냈는데, 그 본문에 `?key=…` 가 들어 있을 수 있다. 그 문구는 화면에도 뜨고 Vercel 로그에도 남는다. 점검표의 「로그에 키를 출력하지 않는다」는 **내가 찍는 것만 조심해서는 안 되고 남이 준 글자도 지워야 한다**는 뜻이었다. `redact()` 를 넣었다 |
| **공백 두 칸짜리 이름이 순위표에 빈 칸을 만들었다** | `(student \|\| "이름 없음").trim()` — 빈 문자열은 「이름 없음」이 되지만 공백 두 칸은 **참**이라 그냥 지나가서 trim 뒤에 빈 이름이 됐다. 순위표에 「이름 없음」과 이름이 안 보이는 칸이 **따로** 생겼다. 다듬고 나서 채우도록 순서를 뒤집었다 |
| **줄바꿈으로 끊긴 인용이 전부 「못 찾음」이 됐다** | 모델은 표의 `\| 24.6% \| 1,203건 \|` 을 한 줄로 옮겨 적는다. 글자를 그대로 비교하면 **맞는 인용이 전부 틀린 인용이 된다.** 공백을 지운 자리표로 원문 구간을 되찾고, 보여 줄 때는 원문 쪽 글자를 보여 준다 |
| **배포한 데서만 서버 함수가 죽었다** | 로컬은 멀쩡했다 — 시험 75건도, esbuild 번들도 통과. 그런데 Vercel 에서 `FUNCTION_INVOCATION_FAILED`. 원인이 **둘**이었다. ① Vercel Node 런타임은 `(req, res)` 로 부르는데 내 핸들러는 `Request→Response` 라 **아무도 응답을 끝내지 않아** 에러가 아니라 **타임아웃**으로 죽었다. ② 상대 import 의 `.ts` 확장자를 못 읽었다. **내가 돌려 본 것과 거기서 도는 것이 같다는 보장이 없다.** import 없는 함수 하나와 import 한 함수 하나를 같이 올려 **갈라서** 찾았다 — 504 와 500 이 갈리는 것이 답이었다 |
| **내 벤치마크가 만점을 줬다** | 실제 제안서를 넣었더니 여섯 항목 전부 수준 4 — **100점**. 강사 벤치마크는 같은 문서에 89점을 줬다. 모델은 concerns 에 「경쟁도가 무엇을 재는 값인지 불분명하다」고 적어 놓고도 데이터 근거에 4 를 줬다 — **내 수준 정의가 그것을 허락했다.** 출처·기간·단위·점검이 다 있으면 만점이 되는 체크리스트였다. **맨 위에서 안 갈리는 자는 자가 아니다.** 수준 4 를 「갖췄다」가 아니라 **「더 물을 것이 없다」**로 고쳤다 |
| **인용 넷 중 넷을 «못 찾음»으로 버렸다** | 모델이 지어낸 줄 알았다. 뜯어 보니 전부 「앞 구절 `...` 뒤 구절」이었고 **조각은 다 원문에 있었다.** 앞뒤 말줄임표만 벗기고 가운데 것은 안 벗긴 것이 이유였다. 모델을 의심하기 전에 **내가 읽는 방식**을 먼저 의심한다. 조각마다 찾고, 원문에 나온 **순서대로**일 때만 인정한다 |
| **못 찾은 인용을 그냥 비웠다** | 그러면 읽는 사람이 「모델이 지어냈다」와 「추출이 글자를 바꿨다」를 가를 수 없다 — 고칠 곳이 정반대인데. 위 진단을 할 수 있었던 것도 그때 원문을 손에 들고 있었기 때문이다. 이제 `attemptedQuote` 로 **모델이 적었던 글자**를 남긴다 |
| **키 모양이 하나가 아니었다** | 오류 문구에서 키를 지우는 `redact()` 가 `AIza…` 만 지우고 있었다. 배포 직전에 번들을 훑다가 알았는데 — **실제로 쓰는 키가 `AQ.` 로 시작했다.** 내가 아는 한 가지 모양만 막고 있었던 것이다. **지우는 쪽은 넓게 잡는다**: 못 지우면 키가 새고, 넘치게 지우면 오류 문구가 조금 덜 친절해질 뿐이다 |
| **키가 틀리면 Google 은 401 이 아니라 400 을 준다** | 가짜 키로 실제 Gemini 를 한 번 불러 보고 알았다. 가이드 12장 증상표는 「키 오류 → 401·403」이라고 적었지만 돌아온 것은 `400 API_KEY_INVALID` 였다. 상태 코드만 보고 「요청 형식이 맞지 않다」고 내면, **키를 고칠 사람이 코드를 뒤진다.** 본문을 보고 가른다 |
| **강조 표시가 별표 그대로 화면에 찍혔다** | 서버 문구에 「고친 뒤 \*\*다시 배포\*\*한다」처럼 강조를 썼는데 화면은 글자로 그렸다. **문구를 쓸 때는 강조로 보이고 화면에서는 안 보인다** — 실브라우저 스크린샷을 찍어야 걸린다. 문구에서 별표를 빼는 대신 그리는 쪽(`src/lib/mark.tsx`)을 고쳤다. 빼면 다음 사람이 또 넣는다 |
| **README 의 배점표는 아무도 다시 안 센다** | 배점을 코드에서 이 문서로 손으로 옮겨 적었다. `my-report` 에서 한 표가 네 파일에 복사돼 어긋나 있던 것과 같은 자리다. `npm run check` 가 이 표를 코드와 대조한다 |

## 실제로 재 봤다

`my-report` 의 제출본 제안서(6,623자)를 넣었다. **강사 벤치마크가 89점을 준 바로 그 문서**다.

| | 자를 고치기 전 | 고친 뒤 | 강사 앱 |
| --- | ---: | ---: | ---: |
| 운영 책임자 | 100 | **88.75** | **89** |
| 재무 책임자 | 88.75 | 80 | — |
| 사업부 리더 | 100 | 80 | — |

깎인 자리도 같았다 — **데이터 근거 3/4, 이유는 「경쟁도가 무엇을 재는 값인지 확인 안 됨」.**
서로 모르는 두 벤치마크가 같은 구멍을 짚었다. 세 번째로 나온 지적은 더 이상 의견이 아니다.

기준 문서 둘로 잰 값(`npm run compare`)은 이렇다.

| | 갖춘 제안서 | 모자란 제안서 | 차이 |
| --- | ---: | ---: | ---: |
| 총점 (세 역할 평균) | 75.8 | 19.6 | — |
| 항목별 수준 차 | — | — | 1.67 ~ 3.00 |
| 역할 사이 총점 폭 | 7.5 | 5.0 | (15 넘으면 경고) |

항목 여섯이 전부 갈리고, 역할을 바꿔도 총점이 크게 안 흔들린다 — **관점은 바뀌고 척도는 안 바뀐다**는 것이 실제로 지켜졌다.

### 같은 문서를 다시 넣으면 점수가 달라진다

같은 문서 · 같은 역할(운영 책임자)로 네 번 돌린 결과다.

| | 점수 |
| --- | ---: |
| 네 번의 값 | 81.25 · 83.75 · 88.75 · **96.25** |
| 폭 | **15점** |

가이드 11-6 이 「서로 다른 실행의 점수가 조금 달라질 수 있다」고 적어 뒀지만,
**15점은 「조금」이 아니다.** 이만큼 흔들리면 문서를 고쳐서 오른 것인지
다시 돌려서 오른 것인지 구분이 안 된다 — 그러면 벤치마크가 아니다.

`temperature` 를 0.2 에서 **0** 으로 내렸다. 그래도 완전히 같아지지는 않는다(모델이 그렇다).

**모델에게 수준만 받기 때문에 흔들리는 폭이 「한 항목 ¼ 배점」 단위로 묶인다.**
총점을 모델에게 맡겼다면 흔들림에 바닥이 없다. 그래도 **등수를 매기는 데는 쓰지 않는다** —
이 점수는 「어디를 먼저 고칠까」를 고르는 데 쓰는 것이다. 그 답은 네 번 모두 같았다:
**데이터 근거 · 경쟁도 정의.**

## 다른 주제로 바꾸려면

1. 평가 대상과 최종 의사결정자를 한 문장으로 정한다.
2. `src/lib/rubric.ts` 의 `CRITERIA` 를 바꾼다 — **배점 합이 100 이 아니면 앱이 뜨지 않는다.**
3. 수준 0~4 를 **관찰 가능한 문장**으로 적는다. 「좋다/나쁘다」가 아니라 「무엇이 보이면」.
4. `REVIEWERS` 의 관점을 바꾼다. 배점은 건드리지 않는다.
5. `verdictOf()` 에 이 주제의 「이것이 없으면 나머지가 다 좋아도 안 된다」를 적는다.
6. `npm test && npm run check` 로 문서와 코드가 갈렸는지 본다.
7. **`npm run compare` 로 기준을 보정한다.** `fixtures/` 의 갖춘 문서와 모자란 문서를
   세 역할로 각각 평가해서 두 가지를 본다 — 항목별 수준이 **충분히 갈리는가**
   (안 갈리면 그 항목의 수준 정의가 모호한 것이다), 그리고 같은 문서의
   **역할 사이 총점이 비슷한가** (크게 갈리면 관점이 척도까지 흔든 것이다).
   Gemini 를 여섯 번 부르니 자주 돌리지 않는다.
